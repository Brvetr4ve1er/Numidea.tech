# Site architecture

The studio's website is a static site of hand-written HTML, CSS and vanilla JavaScript with no framework and no runtime dependency; a few pages and regions are generated by small Node scripts, and only the files listed in `scripts/site.mjs` are ever published (README.md › This repository — the landing page). This map shows which pages exist, how `index.html` and `assets/app.js` are put together, and the small scripts that tie the pages to each other. Start with the page table, then read the `index.html` anatomy; language handling has its own map, [[Languages and RTL]].

## index.html anatomy

### Head

- One inline script runs before the stylesheets: it picks the theme, sets `data-theme` on `<html>`, writes the font preloads and exposes `NUMIDEA_WA` (the WhatsApp number); on the French page alone, a `LANG:fr-only` block first sends a shared `?lang=` or a stored `en`/`ar` preference to that language's page, and sets the canonical URL from the `hreflang` alternates (index.html › the head script; scripts/build-lang.mjs › header). This is the [[Head bootstrap  pre-paint resolver]]; its language hold and `NUMIDEA_LANG` are gone since 2026-10-31 ([[Languages and RTL]]).
- Then three stylesheets in a fixed order: `fonts.css`, `themes.css` (the theme blocks), `styles.css` (layout and components, which only reads the tokens) (index.html › the stylesheet links). Themes are covered in [[Themes and tokens]].
- Two JSON-LD blocks sit in the head: the studio as a `ProfessionalService`, whose description `scripts/build-lang.mjs` writes from the dictionary (index.html › the first ld+json), and the site itself as a `WebSite`, with its name (the `og:site_name`), home URL and three languages (index.html › the second ld+json). A third one, the FAQ as a `FAQPage`, is not in the head but at the end of the body, and `build-lang.mjs` writes it from the dictionary (index.html › #ld-faq). See [[Studio Structured Data (ProfessionalService JSON-LD)]] and [[FAQ Structured Data (ld-faq)]].

## assets/app.js, part by part

`app.js` is one IIFE with no dependencies that honours `prefers-reduced-motion` (assets/app.js › 1). Its parts, in file order:

|---|---|---|

| `ESTIMATE` | estimator model | Pure figures and arithmetic, including `PRICE_MODEL`, so a script can test it without a page (assets/app.js › estimator model). Prices are in [[Pricing and market]] |

| DOM ready | DOM ready | The language switch's links storing the choice, theme switcher, scroll progress, reveal-on-scroll, ambient parallax, hero plate (with `unfold()` for the slides in the template), mobile menu, legacy `#/work` redirect, founder résumé accordion, contact form, the guide's hand-off read on arrival (assets/app.js › DOM ready) |

## Contact and lead flow

1. With JavaScript off, the form posts to a `mailto:` and the browser checks required fields; with it, `app.js` validates and shows its own messages (assets/app.js › contact form).
2. If `NUMIDEA_SUPABASE_URL` and `NUMIDEA_SUPABASE_KEY` are set, the lead is also sent, best effort, to a Supabase `leads` table (assets/app.js › contact form). Both are empty strings today, so this step does nothing (index.html › 1317). The owner keeps it off on purpose (OWNER-CONTENT.md › 11).
3. The mail client opens pre-filled to the site's one address, with a "Source" line from `leadSource()` (`?ref=`, `utm_*`, and whether `fbclid` or `gclid` is present) (assets/app.js › contact form; BRAND.md › Lead source).
4. WhatsApp links append only the `ref` code, as `[ref]` (assets/app.js › 13 · WhatsApp).

Nothing is stored and there are no cookies or analytics (README.md › Features). See [[Lead source without tracking]], [[Contact form flow (validation - optional Supabase insert - mailto)]], [[Supabase lead store (off on purpose)]] and [[_COMMUNITY_i18n and Contact Flow]].

## 404.html

- GitHub Pages serves this page for any missing URL at any depth, so its first head script works out the site root (the repository subpath on `*.github.io`, `/` elsewhere) and `document.write`s the icon, font preloads and stylesheets from it before first paint, with a `<noscript>` copy for JavaScript off (404.html › 10–44). See [[Site-root recomputation for the GitHub Pages 404]].
- Its second head script follows the visitor's stored theme and language, with `?lang=` first, and points the two home links at the site root once the page is parsed; all three languages are always in the markup, and `html[lang]` picks the button label, so no text is swapped after paint (404.html › 81–132).
- The repository copy keeps relative `<noscript>` and home links, so it previews from disk; staging rewrites them to the site root, so the published page is styled at any depth with JavaScript off too (scripts/lib/stage-404.mjs › header). The browser audit opens it two folders down, locally and on an emulated GitHub Pages, with JavaScript on and off (scripts/audit.mjs › header).
